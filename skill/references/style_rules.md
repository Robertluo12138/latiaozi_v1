# 拉条子格式规则书（强制）

本文件是拉条子写作的强制规则。SKILL.md 是入口与简述；本文件是细则与判定标准。出稿前如对任何形态拿不准，回到此文件比对。

## 一、层级结构

### 1.1 总论点
- 全文唯一一条，加粗
- 必须包含"经营整体态势 + 关键结构性判断"
- 长度 12–28 字
- 形态：结论 + 限定词
- 例：`本月经营稳中有进结构性隐忧需提前修复`
- 例：`双 11 数据保障整体达标实时链路存在单点风险`

### 1.2 一级论点
- 数量：3–5 条
- 加粗
- 每条是一句结论式判断
- 长度 10–22 字
- 不得出现字段名式标签
- 常用归类范式（择一）：
  - 经营结果 / 经营动作 / 经营隐忧 / 后续动作
  - 进展 / 数据 / 风险 / 下一步
  - 业务问题 / 数据现象 / 根因判断 / 行动建议
  - 现状 / 抓手 / 风险 / 节奏

### 1.3 二级子论点
- 每个一级下 2–4 条
- 强制结构：`**短判断：** 事实 + 数据 + 解释 + 判断`

## 二、短判断（冒号前）

### 2.1 长度
- 通常 8–18 个汉字（数字与英文按视觉占位计入）
- 极限可放宽到 6–22 字
- 严禁短到只剩字段名（≤ 5 字几乎一定是字段名）

### 2.2 禁用标点（绝对）

冒号前不得出现以下任一字符：

| 字符 | 名称 |
|---|---|
| `,` | 英文逗号 |
| `.` | 英文句号（注意：会破坏数字如 0.8） |
| `;` | 英文分号 |
| `，` | 中文逗号 |
| `。` | 中文句号 |
| `；` | 中文分号 |
| `、` | 顿号 |

允许使用：阿拉伯数字、英文字母（仅作为术语如 GMV / SOP / DAU）、中文字符、空格、`+` `-` `%`。

> 注：若需引入小数（如 0.8），将其挪到冒号后正文，短判断仅描述方向（如"持续下行""明显下行"）。

### 2.3 禁用形态：字段名标签

以下形态一律禁止作为短判断：

| 禁用 | 原因 |
|---|---|
| `GMV：` | 字段名，没有判断 |
| `订单：` | 字段名 |
| `客单价：` | 字段名 |
| `数据集：` | 字段名 |
| `看板：` | 字段名 |
| `SQL：` | 字段名 |
| `本月数据：` | 字段名 + 时间，仍是标签 |
| `用户增长情况：` | 等价字段名，"情况"是无判断的占位词 |

判定法：如果短判断本身没有"动词 / 形容词 / 趋势词 / 判断词"，就一定是标签。

### 2.4 推荐句型

| 句型 | 适用 |
|---|---|
| `X 保持增长环比提升` | 正向延续 |
| `X 增长但增速偏低` | 正向但有结构问题 |
| `X 环比改善仍未达预期` | 改善但不够 |
| `X 完成度达标质量待观察` | 数量完成但质量未知 |
| `X 进度滞后亟需补位` | 落后于计划 |
| `X 结构性风险初步显现` | 风险预警 |
| `X 落地可控但聚焦不够` | 落地了但散 |
| `X 上线支撑日级追踪` | 工具能力上线 |
| `X 治理后查询性能提升` | 治理类成果 |
| `X 单点风险需结构性修复` | 单点暴露 |

## 三、正文（冒号后）四要素

四要素允许融合在 1–3 句中文句子内，但每段必须可被拆出以下四件事：

### 3.1 事实
- 发生了什么动作或现象
- 例："本月新增订单宽表上线"
- 例："完成大促拉新计划"

### 3.2 数据
- 具体数字、占比、环比、同比、绝对值或区间
- 缺失时使用 `待补充：XX数据`，绝不虚构

### 3.3 解释
- 数据背后的机制、原因、结构变化
- 例："主要由家电类目客单提升驱动"
- 例："活动空窗期与活跃下行窗口高度重合"

### 3.4 判断
- 对经营的意义 / 风险 / 下一步含义
- 例："拉新质量与承接动作存在断点应优先排查首单后 7 日触达"

整段建议不超过 80 字。超过即应拆分或压缩。

## 四、业务价值语言（强制转换）

不要写"做了什么"，要写"做了什么对业务意味着什么"。

| 执行语言（不要） | 业务价值语言（要） |
|---|---|
| 建了一张订单宽表 | 订单宽表上线支撑多维经营分析 |
| 跑了一次 SQL | 完成订单回流校验数据一致性达标 |
| 上线了一个看板 | 经营看板上线管理层可日级追踪核心指标 |
| 优化了表结构 | 表结构治理后 BI 查询性能提升使用门槛降低 |
| 接了 N 个需求 | 完成 N 项业务分析需求支撑业务决策 |
| 修了几个 bug | 修复 N 个数据口径问题报表一致性恢复 |
| 写了文档 | 完成数据资产文档沉淀降低跨团队协作成本 |
| 加了告警 | 监控告警颗粒度细化异常发现链路前移 |
| 优化了 SQL 查询 | 核心查询耗时压回健康线减少 BI 等待时间 |

## 五、数据缺失处理

| 情景 | 处理 |
|---|---|
| 原文给出具体数字 | 直接使用 |
| 原文只给方向（"涨了""降了"） | 保留方向词 + 补占位 `待补充：具体变化幅度` |
| 完全没有数据 | 整段保留事实 / 解释 / 判断，数据位用 `待补充：XX数据` |
| 用户暗示但未明说 | 不得推断为具体数字，按"完全没有"处理 |

**绝对禁止**：把"涨了一些""不少""挺多"翻译成具体百分比或数字。

## 六、语气与禁忌

### 6.1 禁止口语
"我们觉得 / 大概 / 应该 / 差不多 / 估计 / 感觉 / 蛮 / 挺 / 还行 / 没毛病"

### 6.2 禁止空泛副词（无数据支撑时）
"非常 / 极大 / 巨大 / 显著 / 极其 / 大幅 / 大量 / 大规模 / 全面"

### 6.3 禁止符号
- 不使用感叹号 `！` `!`
- 不使用 emoji
- 不使用问号制造悬念

### 6.4 禁止结构
- 不输出"以上即为本月汇报""感谢领导审阅"
- 不输出过渡句"接下来""下面""然后我们看到"
- 不输出客套开场"领导好""各位同事"
- 不输出"由于篇幅原因""限于时间"等推诿

## 七、长度上限

| 项 | 上限 |
|---|---|
| 全文（不含原文） | 800 字 |
| 一级论点数 | 5 |
| 单一级下二级数 | 4 |
| 单条二级正文 | 80 字 |
| 短判断 | 22 字 |
| 总论点 | 28 字 |

## 八、出稿顺序约束

如果使用"经营结果 / 经营动作 / 经营隐忧 / 后续动作"范式，必须按此顺序排列，不得颠倒：

- 隐忧不得放在最后被"后续动作"掩盖
- 后续动作必须收口在最末，避免悬空
- 一级论点之间必须能形成"问题 → 抓手"的因果链

## 九、Markdown 形态

- 总论点：单独一行，前后空行，加粗
- 一级论点：单独一行，前后空行，加粗
- 二级子论点：使用无序列表 `-`，每条独立一行
- 不使用一级标题 `#`、二级标题 `##` 等
- 加粗使用 `**...**`，不要使用斜体或其他格式
