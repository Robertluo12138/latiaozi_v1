# 拉条子格式规则书（强制）

本文件是拉条子写作的强制规则。SKILL.md 是入口与简述；本文件是细则与判定标准。出稿前如对任何形态拿不准，回到此文件比对。

## 一、层级结构

### 1.1 总论点
- 全文唯一一条，加粗
- 必须包含"经营整体态势 + 关键结构性判断"
- 长度 12–28 字
- 形态：结论 + 限定词
- 例：`本月经营稳中有进结构性隐忧需提前修复`
- 例：`双 11 数据保障整体达标实时链路存在单点风险`

### 1.2 一级论点
- 数量：3–5 条；**月报多工作流场景上限至 6 条**（详见第十节）
- 加粗
- 每条是一句结论式判断
- 长度 10–22 字
- 不得出现字段名式标签
- 常用归类范式（择一）：
  - 经营结果 / 经营动作 / 经营隐忧 / 后续动作
  - 进展 / 数据 / 风险 / 下一步
  - 业务问题 / 数据现象 / 根因判断 / 行动建议
  - 现状 / 抓手 / 风险 / 节奏
  - **多工作流并行**：按工作流独立成一级（每条工作流一个一级，附带各自的下月动作）

### 1.3 二级子论点
- 每个一级下 2–4 条
- 强制结构：`**短判断：** 事实 + 数据 + 解释 + 判断`

## 二、短判断（冒号前）

### 2.1 长度
- 通常 8–18 个汉字（数字与英文按视觉占位计入）
- 极限可放宽到 6–22 字
- 严禁短到只剩字段名（≤ 5 字几乎一定是字段名）

### 2.2 禁用标点（绝对）

冒号前不得出现以下任一字符：

| 字符 | 名称 |
|---|---|
| `,` | 英文逗号 |
| `.` | 英文句号（注意：会破坏数字如 0.8） |
| `;` | 英文分号 |
| `，` | 中文逗号 |
| `。` | 中文句号 |
| `；` | 中文分号 |
| `、` | 顿号 |

允许使用：阿拉伯数字、英文字母（仅作为术语如 GMV / SOP / DAU）、中文字符、空格、`+` `-` `%`。

> 注：若需引入小数（如 0.8），将其挪到冒号后正文，短判断仅描述方向（如"持续下行""明显下行"）。

### 2.3 禁用形态：字段名标签

以下形态一律禁止作为短判断：

| 禁用 | 原因 |
|---|---|
| `GMV：` | 字段名，没有判断 |
| `订单：` | 字段名 |
| `客单价：` | 字段名 |
| `数据集：` | 字段名 |
| `看板：` | 字段名 |
| `SQL：` | 字段名 |
| `本月数据：` | 字段名 + 时间，仍是标签 |
| `用户增长情况：` | 等价字段名，"情况"是无判断的占位词 |

判定法：如果短判断本身没有"动词 / 形容词 / 趋势词 / 判断词"，就一定是标签。

### 2.4 推荐句型

| 句型 | 适用 |
|---|---|
| `X 保持增长环比提升` | 正向延续 |
| `X 增长但增速偏低` | 正向但有结构问题 |
| `X 环比改善仍未达预期` | 改善但不够 |
| `X 完成度达标质量待观察` | 数量完成但质量未知 |
| `X 进度滞后亟需补位` | 落后于计划 |
| `X 结构性风险初步显现` | 风险预警 |
| `X 落地可控但聚焦不够` | 落地了但散 |
| `X 上线支撑日级追踪` | 工具能力上线 |
| `X 治理后查询性能提升` | 治理类成果 |
| `X 单点风险需结构性修复` | 单点暴露 |

## 三、正文（冒号后）四要素

四要素允许融合在 1–3 句中文句子内，但每段必须可被拆出以下四件事：

### 3.1 事实
- 发生了什么动作或现象
- 例："本月新增订单宽表上线"
- 例："完成大促拉新计划"

### 3.2 数据
- 具体数字、占比、环比、同比、绝对值或区间
- 缺失时使用 `待补充：XX数据`，绝不虚构

### 3.3 解释
- 数据背后的机制、原因、结构变化
- 例："主要由家电类目客单提升驱动"
- 例："活动空窗期与活跃下行窗口高度重合"

### 3.4 判断
- 对经营的意义 / 风险 / 下一步含义
- 例："拉新质量与承接动作存在断点应优先排查首单后 7 日触达"

整段建议不超过 80 字。超过即应拆分或压缩。

## 四、业务价值语言（强制转换）

不要写"做了什么"，要写"做了什么对业务意味着什么"。

| 执行语言（不要） | 业务价值语言（要） |
|---|---|
| 建了一张订单宽表 | 订单宽表上线支撑多维经营分析 |
| 跑了一次 SQL | 完成订单回流校验数据一致性达标 |
| 上线了一个看板 | 经营看板上线管理层可日级追踪核心指标 |
| 优化了表结构 | 表结构治理后 BI 查询性能提升使用门槛降低 |
| 接了 N 个需求 | 完成 N 项业务分析需求支撑业务决策 |
| 修了几个 bug | 修复 N 个数据口径问题报表一致性恢复 |
| 写了文档 | 完成数据资产文档沉淀降低跨团队协作成本 |
| 加了告警 | 监控告警颗粒度细化异常发现链路前移 |
| 优化了 SQL 查询 | 核心查询耗时压回健康线减少 BI 等待时间 |

## 五、数据缺失处理

| 情景 | 处理 |
|---|---|
| 原文给出具体数字 | 直接使用 |
| 原文只给方向（"涨了""降了"） | 保留方向词 + 补占位 `待补充：具体变化幅度` |
| 完全没有数据 | 整段保留事实 / 解释 / 判断，数据位用 `待补充：XX数据` |
| 用户暗示但未明说 | 不得推断为具体数字，按"完全没有"处理 |

**绝对禁止**：把"涨了一些""不少""挺多"翻译成具体百分比或数字。

## 六、语气与禁忌

### 6.1 禁止口语
"我们觉得 / 大概 / 应该 / 差不多 / 估计 / 感觉 / 蛮 / 挺 / 还行 / 没毛病"

### 6.2 禁止空泛副词（无数据支撑时）
"非常 / 极大 / 巨大 / 显著 / 极其 / 大幅 / 大量 / 大规模 / 全面"

**禁止"看似克制实则放大"短语**（除非用户原文明确使用）：

- 明显提升 / 大幅提升（暗示具体涨幅但无数据支撑）
- 完全打通 / 闭环完成（绝对化，多数仍属"初步"）
- 零门槛 / 全自动（绝对化，几乎不可能成立）

均参见第十一节"月报忠实扩写"11.4 节的克制型替换表。

### 6.3 禁止符号
- 不使用感叹号 `！` `!`
- 不使用 emoji
- 不使用问号制造悬念

### 6.4 禁止结构
- 不输出"以上即为本月汇报""感谢领导审阅"
- 不输出过渡句"接下来""下面""然后我们看到"
- 不输出客套开场"领导好""各位同事"
- 不输出"由于篇幅原因""限于时间"等推诿

## 七、长度上限

| 项 | 上限 |
|---|---|
| 全文（不含原文） | 800 字 |
| 一级论点数 | 5（月报多工作流场景可至 6） |
| 单一级下二级数 | 4 |
| 单条二级正文 | 80 字 |
| 短判断 | 22 字 |
| 总论点 | 28 字 |
| `待补充：` 占位符 | 全文 ≤ 2（用户显式要求数据完整性盘点除外） |

## 八、出稿顺序约束

如果使用"经营结果 / 经营动作 / 经营隐忧 / 后续动作"范式，必须按此顺序排列，不得颠倒：

- 隐忧不得放在最后被"后续动作"掩盖
- 后续动作必须收口在最末，避免悬空
- 一级论点之间必须能形成"问题 → 抓手"的因果链

## 九、Markdown 形态

- 总论点：单独一行，前后空行，加粗
- 一级论点：单独一行，前后空行，加粗
- 二级子论点：使用无序列表 `-`，每条独立一行
- 不使用一级标题 `#`、二级标题 `##` 等
- 加粗使用 `**...**`，不要使用斜体或其他格式

加粗结构铁律（落到月报真实场景）：

- 必须有 1 条加粗总论点
- 必须有若干条加粗一级论点
- 每条二级子论点冒号前的短判断必须加粗
- 仅扫读所有加粗位即应能看懂全文核心结论；如果加粗位被去掉后仍能读出完整意思，说明加粗结构没承载判断，必须返工

## 十、真实月报场景下的保真规则

实际企业月报往往包含多条相互独立的工作流（4–6 条），且口语化、信息密度不一。在这类场景下，**"完整性"优先于"美感型压缩"**。

### 10.1 保留主工作流

- 原文中清晰可分的 4–6 条工作流，**默认全部保留为一级论点**
- 不得为了让结构看起来"更整齐"而把两条独立项目合并到一起
- 当且仅当两条工作流在事实层面高度耦合（同一项目的两个阶段 / 同一目标下的两个抓手），才合并

### 10.2 不得静默丢弃

- 任何在原文中独立成段的工作流，都必须在输出中以一级论点形式出现
- 即使该工作流信息密度低（只有动作没有结果），仍诚实写出"初步推进 / 形成雏形"或保留事实
- 信息密度低不是丢弃理由

### 10.3 不要把月报改写为通用总结

- 不要把"5 个项目的月报"输出成 3 条结构化总结
- 月报本质是月度多工作流并行的状态扫描，**结构化扫描不应损失工作流颗粒度**
- 输出应当让事业部老板一眼看出"这个月推进了几条工作流，每条进展到哪里"

### 10.4 工作流顺序保留

- 当用户原文中工作流的顺序已合理（按重要性 / 项目独立性 / 时间线 / 依赖关系），**保留原顺序**
- 不要为了套用"经营结果 / 经营动作 / 隐忧 / 后续动作"范式强行重排

### 10.5 改写措辞但不重写事实

- 允许：把"安装比之前简单多了"改写为"安装链路完成打通使用门槛降低"
- **禁止**：把"安装比之前简单多了"改写为"零门槛安装"
- 即口径上提升专业度，但不得把模糊表达放大成绝对化判断
- 用户没说"全自动 / 大幅 / 完全打通 / 闭环完成"，输出就不准引入这些放大词

### 10.6 二级标题语义形态（落到月报场景）

月报二级标题应当是 **"动作 + 结果 / 状态 + 业务意义"** 的结构。

- ❌ 工具名 / 平台名 / 项目代号作为标题（如 `ODPS 工具链：` / `Qoderwork 数据连接：` / `FBI 看板：`）
- ✅ 业务化短判断（如 `双端安装链路完成打通：` / `数据连接底座初步建成：` / `货品诊断视角持续补齐：`）

判定法：把月报标题给一个不知道工具名的事业部老板看，他能否一句话理解"做了什么 + 什么状态 + 对业务有何意义"。

## 十一、月报忠实扩写（faithful expansion）

月报是月度多工作流并行的状态扫描，**不是工具名速记**。压缩到每条一级只剩一句二级、整篇全是四五字标题的输出，对一个事业部老板而言无法判断进展、无法做下月安排——属于**"过度压缩"**。

本节是对第十节"工作流完整性"的延伸：第十节解决"几条工作流"，本节解决"每条工作流写多少"。

### 11.1 忠实扩写的定义

允许在保留每条工作流原始事实的前提下，**从单一"做了什么"扩写为四件事**：

| 维度 | 含义 |
|---|---|
| 做了什么 | 用户明确写到的事实 / 动作 / 当前状态 |
| 解决了什么问题 | 这个动作消除或缓解了哪个原本痛点（推得自原文） |
| 创造了什么业务/团队价值 | 对业务、用户、团队协同节奏的意义（推得自原文） |
| 支撑了什么后续能力 | 为下一步迭代、复用、沉淀提供了什么基础（推得自原文） |

关键词是 **"推得自"**——所有扩写内容必须能从用户原文事实里**自然推得**，不是模型自由补充。

### 11.2 严禁虚构（与第五节数据缺失处理叠加）

模型在做月报扩写时，**绝对不得**凭空引入用户原文中没有的：

| 禁止虚构 | 反例 |
|---|---|
| 新数字 / 新指标 / 新百分比 | 原文未给数 → 输出 `使用率提升 80%` |
| 新业务结果 | 原文只说工具上线 → 输出 `GMV 拉动 5%` |
| 新项目 / 新工作流 | 原文 5 条工作流 → 输出 6 条（多出来一条没出处） |
| 新用户反馈 / 新满意度评价 | 原文未提反馈 → 输出 `团队反馈极佳` |
| 新采纳率 / 新落地状态 | 原文说"还在迭代" → 输出 `产品化落地完成` |
| 新系统能力 / 新功能 / 新接入方 | 原文未提 X 接入 → 输出 `已接入下游 X 系统` |

判定法（写完每条二级问三件事）：

1. 这件事用户原文写过吗？
2. 这条二级所承载的"问题 / 价值 / 后续"，是从原文事实**自然推得**的，还是我"自己补"上去的？
3. 让用户对着原文逐句核对，他能否说"是的，意思就是这个"？

任一答"否"，删掉或改写。

### 11.3 月报扩写量级约束

| 项 | 约束 |
|---|---|
| 一级论点数 | 4–6 条（与第十节一致；输入 4–6 条工作流必须保留 4–6 条一级） |
| 单一级下二级数 | **通常 2–3 条** |
| 一级仅含 1 条二级 | **例外**——仅在原文该工作流信息确实极少（一两句话）时使用，正常月报不允许出现 |
| 单条二级长度 | ≤ 80 字（与第七节一致）|
| 二级正文应当铺陈的维度 | 动作 / 事实 + 解决的问题 + 业务价值或后续意义 |
| 全文长度（月报场景）| 通常 900–1300 中文字（足以承载 5 条工作流的扩写） |

### 11.4 扩写边界（语气克制）

扩写是"把价值说清楚"，**不是"把语气放大"**。即使为了让标题"够有力"，也不得引入用户原文未出现的放大型词。

**严禁引入的放大型词**（除非用户原文明确使用）：

- 明显提升
- 大幅提升
- 完全打通
- 零门槛
- 全自动
- 闭环完成

> 注：本表与第六节 6.2、SKILL.md "业务措辞克制" 保持一致。`明显提升` 与 `大幅提升` 同等量级——都暗示具体涨幅，但通常无数据支撑，属于"看似克制实则放大"。

**优先使用克制型替换**：

| 放大型 | 克制型 |
|---|---|
| 零门槛 | 降低使用门槛 / 减少重复支持成本 |
| 大幅提升 / 明显提升 | 提升至 ... 水位（有数据时）/ 改善 / 较此前简化 |
| 完全打通 | 初步打通 / 链路打通 |
| 全自动 | 自动化（保留半自动事实）|
| 闭环完成 | 基本跑通 / 形成雏形 / 链路初步闭环 |
| 产品化落地 | 形成 Demo 雏形 / 初步可试用 |
| 支撑全流程 | 为后续迭代提供基础 / 支撑后续沉淀 |

### 11.5 扩写边界示例

| 用户原文（粗糙） | ✅ 忠实扩写 | ❌ 自由扩写（虚构） |
|---|---|---|
| "mac 和 windows 双端都搞定了，安装比之前简单多了" | 双端安装链路完成打通，相较此前安装较为简化，团队同事已开始使用，使用门槛下行 | 双端安装零门槛，使用率大幅提升至 80% |
| "Agent 工作台接了几个数据源，能跑基础查询" | Agent 工作台已接入若干数据源，可支撑基础查询场景跑通，形成数据连接初步底座 | Agent 工作台接入 12 个数据源，覆盖率 95%，全自动化分析 |
| "AI 报告链路在探索，准确性还要看" | 大模型月报生成链路初步跑通，已可生成月报草稿，准确性仍需进一步观察 | AI 报告闭环完成，月报生成完全替代人工，效率显著提升 |
| "经营看板加了几个维度，老板反馈整体可用" | 经营看板分析维度持续补齐，老板反馈整体可用，管理层看数视角逐步扩展 | 经营看板大幅升级，覆盖全部业务场景，使用满意度极高 |

判定法：左列是用户写过的，右列是模型自己加的——任何"看起来更漂亮"但用户没说过的内容都属于右列，必须删除。

### 11.6 写完自检（与 checklist 第 10 项叠加）

每条二级写完后，扫一遍：

1. 这条短判断里**有没有用户原文未给的数字 / 指标 / 比例**？有 → 删除或改为定性表述。
2. 这条正文里**有没有"明显提升 / 大幅 / 完全打通 / 零门槛 / 全自动 / 闭环完成"**这类放大词？有 → 替换为克制型。
3. 这条所承载的"问题 / 价值 / 后续"是不是**模型自己想出来的**？是 → 改为更贴近原文的表述，或删除。
4. 这条短判断扣掉所有数据后，**还能不能反向回到用户原文**？不能 → 说明已偏离事实，必返工。
