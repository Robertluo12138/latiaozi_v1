# 阿里风格拉条子写作技能

## 何时使用

当用户提交中文工作汇报类原文，并希望改写为管理者会前可快速扫读的结构化写作时使用。

常见触发表达：
- "改成拉条子" / "阿里风格" / "结论先行"
- "重写月报 / 周报 / 复盘 / 总结"
- "结构化一下这个汇报"
- "管理者风格" / "老板要看的"

适用原文类型：月报、周报、项目复盘、数据分析结论、SQL/建表进度、BI看板汇报、业务诊断、经营分析。

## 输出形态铁律（最高优先级）

无论上下文如何，本技能的回复**只输出最终改写后的拉条子内容**，且**必须从加粗总论点开始**。所有思考、抽取、归类、拟标过程一律内部默执行，**不得在输出中显形**。

### 严禁出现的"过程性"片段

| 类别 | 严禁短语（举例） |
|---|---|
| 流程引导 | "现在我来按照拉条子规范……" / "下面我开始" / "首先我会" |
| 抽取宣告 | "先做抽取" / "原文事实抽取" / "事实抽取如下" |
| 归类宣告 | "归桶" / "归类如下" / "我先把它分成几个一级" |
| 改写引导 | "以下是改写结果" / "改写如下" / "下面给出改写" |
| 自我总结 | "以上即为改写" / "整体改写完毕" / "希望能帮到您" |
| 客套开场 | "好的" / "明白" / "收到" / "下面汇报" |

判定法：如果一段文字描述的是"我正在做什么"或"我接下来要做什么"，而不是"对业务的判断"，就是过程性内容，必须删除。

### 加粗结构铁律（不得弱化）

输出**必须**严格使用以下三层加粗结构，缺一不可：

1. **一条加粗总论点**（首行，前后留空行）
2. **若干条加粗一级论点**（每条独立一行，前后留空行）
3. **每个二级子论点冒号前的加粗短判断**（形如 `**短判断：** 正文`）

仅扫读所有加粗位即应能看懂全文核心结论。如果加粗位被去掉后仍能读出完整意思，说明加粗结构没有承载判断，必须返工。

### 输出从首字符即为加粗总论点

- 不写"好的""明白""收到""下面是改写"等开场
- 不写"如上"——更不写"以上即为本次改写结果"等收口

## 输出层级（强制三层）

1. **总论点（1 条）** — 加粗。一句话点明本次汇报核心结论。
2. **一级论点（3–5 条；月报多工作流场景上限至 6 条）** — 加粗。每条是一句结论式判断（不是字段名）。
3. **二级子论点（每个一级下 2–4 条）** — 每条按下方强制格式书写。

## 二级子论点强制格式

```
**[短判断无标点]：** 事实 + 数据 + 解释 + 判断。
```

### 冒号前（短判断）硬约束

| 项 | 要求 |
|---|---|
| 长度 | 通常 8–18 个汉字 |
| 形态 | 结论式短句，不是字段名 |
| 禁用标点 | `,` `.` `;` `，` `。` `；` `、` 一律不得出现 |
| 禁用空标签 | `GMV：` `订单：` `客单价：` `数据集：` `看板：` `SQL：` 等单纯字段名一律不得作为短判断 |
| 禁用工具/平台名独立成标 | 仅写 `ODPS 工具链：` / `自助分析平台：` / `经营看板：` 这类工具名或平台名，不得作为短判断 |

判定法：去掉冒号后能不能读出"判断"？读不出就是字段名，必返工。

### 二级标题语义形态（落到月报场景的强约束）

二级标题必须是 **"动作 + 结果 / 状态 + 业务意义"** 的结构，让一个不熟悉工具名的事业部老板也能一眼看懂"做了什么 + 当前是什么状态 + 对业务有何意义"。

| ❌ 工具名 / 平台名标题 | ✅ "动作 + 结果 + 业务意义"标题 |
|---|---|
| `ODPS 工具链：` | `双端安装链路完成打通：` |
| `Qoderwork 数据连接：` | `数据连接底座初步建成：` |
| `FBI 看板：` | `货品诊断视角持续补齐：` |
| `自助分析平台：` | `业务侧自助拖拽跑通主路径：` |
| `AI 报告：` | `大模型月报生成跑通基础链路：` |

### 冒号后（正文）四要素

按顺序铺陈，可融合在 1–3 个完整中文句子内：

- **事实**：发生了什么动作 / 结果 / 现象
- **数据**：具体数字、占比、环比、同比、绝对值或区间
- **解释**：数据背后的原因 / 机制 / 结构性变化
- **判断**：对经营的意义、风险、或下一步含义

整段建议不超过 80 字。

## 业务价值语言（必做转换）

将"执行语言"改写为"业务价值语言"：

| 执行语言（不要） | 业务价值语言（要） |
|---|---|
| 建了一张订单宽表 | 订单宽表上线支撑多维经营分析 |
| 跑了一次 SQL | 完成订单回流校验数据一致性达标 |
| 上线了一个看板 | 经营看板上线管理层可日级追踪核心指标 |
| 优化了表结构 | 表结构治理后 BI 查询性能提升使用门槛降低 |
| 接了 N 个需求 | 完成 N 项业务分析需求支撑业务决策 |

## 管理者阅读偏好（强约束）

阿里风格拉条子的核心约束之一是：**管理者只读加粗文字也能抓到核心结论**。请按以下要求收口：

- **加粗结构自洽**：仅扫读总论点 + 一级论点 + 二级标题（冒号前），即可完整把握本次汇报的核心逻辑链。
- **加粗即结论非分类**：加粗位必须是结论式短判断，承载"是好是坏 / 是涨是跌 / 是稳是险"，不得是分类标签或字段名。
- **避免空泛归类标题**：禁止仅写 `经营情况`、`数据建设`、`问题风险`、`本月情况`、`后续工作` 等无判断的归类标题；如需沿用此类范式，必须叠加明确判断（如 `经营结果环比改善但增长结构偏单点` 而非 `经营情况`）。
- **加粗位不解释只判断**：事实、数据、机制解释一律放在冒号后正文，加粗位不堆细节，单条扫读即能给出判断。

## 工作流完整性（多工作流场景必读）

针对月报、季度复盘、年中汇报这类"多工作流并行"输入：

### 强约束

- 当原文清晰呈现 **4–6 条相互独立的工作流**时，**优先保留为 4–6 条独立的一级论点**，而非强行压缩到 3 条
- 月报场景中"完整性"优先于"美感型压缩"：宁可一级数量略多（最多 6 条），也不要把不同项目硬塞进同一条
- 当且仅当两条工作流在事实层面高度耦合（同一项目的不同阶段 / 同一目标下的两个抓手），才合并

### 一级论点数量调整

- 一般场景：3–5 条
- 月报多工作流场景：3–6 条（上限放宽至 6 条）
- 6 条以上：必须做合并取舍

### 顺序保留

- 用户原文中工作流之间已经有合理顺序时（按项目独立性 / 业务重要性 / 时间线），**保留原顺序**
- 不要为了套用"经营结果 / 经营动作 / 隐忧 / 后续动作"范式强行重排

### 不得静默丢弃

- 任何在原文中独立成段的工作流，都不得在输出中被省略
- 如某条工作流信息密度低（只有动作没有结果），仍以一级论点形式保留，并诚实写出"初步推进"或用业务价值语言描述其意义
- **不要把"5 条独立工作流的月报"输出成 3 条结构化总结**——月报本质是月度多工作流并行的状态扫描，结构化扫描不应损失工作流颗粒度

## 业务措辞克制（强约束）

绝不超出用户事实做"放大型表达"。即便用户语气模糊或乐观，也必须以克制、商务的拉条子风格收口。

### 禁用放大型词汇（除非用户原文明确使用）

| 禁用 | 原因 |
|---|---|
| 零门槛 | 绝对化，几乎不可能成立 |
| 大幅 | 副词放大，需要数据支撑 |
| 完全打通 | 绝对化，多数场景仍属"初步" |
| 全自动 | 绝对化，常常是半自动 |
| 闭环完成 | 绝对化，多数仍是"链路初步跑通" |
| 显著 / 极大 / 巨大 | 副词放大，无数据支撑时滥用 |

### 推荐替换（克制型业务措辞）

| 放大型 | 克制型 |
|---|---|
| 零门槛 | 降低使用门槛 |
| 大幅提升 | 明显提升 / 提升至 ... 水位 |
| 完全打通 | 初步打通 / 链路打通 |
| 全自动 | 自动化（保留半自动事实） |
| 闭环完成 | 基本跑通 / 形成雏形 / 链路初步闭环 |

### 措辞偏好原则

- 当用户写"成功""跑通""上线"时：用"完成上线" / "链路打通"，**不升级为"全面贯通"**
- 当用户写"做了一版 demo / 雏形"时：用"形成雏形" / "Demo 跑通"，**不升级为"产品化落地"**
- 当用户写"还在观察 / 还需迭代"时：用"持续观察 / 待迭代"，**不掩盖为"达成阶段目标"**
- 即使为了让标题"够有力"，也不得把方向性判断写成绝对化判断

## 缺数据时的处理（不得虚构 + 不得滥用占位符）

### 禁止虚构

- 绝对禁止编造数字、占比、环比、同比

### 占位符使用边界

`待补充：XX数据` 仅在以下情况使用：

1. 该指标是该段二级论点的核心结论（缺它，论点站不住）
2. 用户原文清晰暗示此处应有数据（如"涨了一些"指方向但未给数）
3. 该数据是经营决策的关键依据（管理层会前必看）

**正常月报改写中，全文 `待补充：` 不超过 2 处**。仅当用户**显式要求**做"数据完整性盘点"或"数据齐备性检查"时不受 2 处限制。

### 不应使用占位符的情况

- 数据可有可无、用方向词或定性判断替代不损失结论的情况
- 仅为"显得严谨"而堆叠的字段（如"覆盖三域字段共 待补充：字段总数"——字段总数本就不影响结论）
- 已经写了定性判断的句子，不要再叠加占位符

### 替代方案：定性判断

如果原文既无数据也无方向词，**优先写定性判断而非占位符**。

- ❌（占位符滥用）：`覆盖支付、退款、物流三域字段共 待补充：字段总数`
- ✅（定性判断）：`覆盖支付、退款、物流三域字段，BI 多维交叉查询无需多表 join`

## 语气

- 克制、商务、扫读友好
- 不出现："我们觉得 / 大概 / 应该 / 差不多 / 估计 / 感觉"
- 不滥用："非常 / 极大 / 巨大 / 显著 / 大幅"（除非有具体数据支撑）
- 不出现感叹号 `！` `!`
- 不输出客套开场白与结尾感谢

## 工作流（内部默执行 / 不得在输出中出现）

以下 6 步是模型在内部需要完成的处理。**任何一步都不得在输出中显形**：不得宣告"我现在开始抽取"，不得列出"原文事实抽取如下"，不得说"以下是改写结果"。模型直接以加粗总论点作为输出的第一行。

1. **抽取（默）**：从原文捞出所有事实、动作、数字、原因、风险、下一步
2. **归类（默）**：归入 3–5 条（月报多工作流可至 6 条）一级论点。常用归类范式：
   - 经营结果 / 经营动作 / 经营隐忧 / 后续动作
   - 进展 / 数据 / 风险 / 下一步
   - 业务问题 / 数据现象 / 根因判断 / 行动建议
   - **多工作流场景**：按工作流独立成一级（每条工作流一个一级，附带各自的下月动作）
3. **拟标（默）**：为每条二级子论点拟一个 8–18 字短判断（无禁用标点、非字段名、动作 + 结果 + 业务意义）
4. **填段（默）**：用 1–3 句话补齐"事实 + 数据 + 解释 + 判断"
5. **回写总论点（默）**：基于一级论点回写一句加粗总论点
6. **自检（默）**：执行 `references/checklist.md` 12 项检查后再输出

输出形态：以加粗总论点起笔，以最后一条二级子论点收尾。

## 输出长度

- 最终全文（不含原文回放）一般不超过 800 字
- 一级论点 3–5 条；月报多工作流场景上限至 6 条
- 每个一级下二级 ≤ 4 条
- 单条二级正文 ≤ 80 字
- `待补充：` 占位符正常场景下不超过 2 处

## 完整输出形态示例（精简）

> **本月经营整体稳中有进结构性隐忧需提前修复**
>
> **经营结果环比改善但增长结构偏单点**
>
> - **GMV 保持增长环比提升：** 本月 GMV 2.3 亿，环比 +8%，盘子较上月扩大约 1700 万，说明经营动作对结果端有正向拉动。
> - **订单规模增长但增速偏低：** 本月订单 120 万，环比 +5%，低于 GMV 增速 3 个百分点，增长更多来自客单提升而非订单扩张。
>
> **经营隐忧需提前暴露**
>
> - **新客次月留存承压：** 次月留存 待补充：次月留存数据，仍处下行通道，反映拉新质量与承接动作之间存在断点，应优先排查首单后 7 日触达。
>
> **后续动作聚焦两件事**
>
> - **优先修复新客次月留存：** 立项次月留存专项，由用户增长团队负责，月底前完成首单后 7 日触达 + 14 日召回 SOP 落地。
> - **私域触达节奏对齐目标：** 私域运营节奏由月触达 2 次提升至 4 次，目标本月完成沉淀进度追平计划。

## 关键对照（再次强调）

**❌ 字段名式标签（禁止）**
> **GMV：** 本月GMV 2.3亿，环比增长8%。

**✅ 结论式短判断（要求）**
> **GMV保持增长环比提升：** 本月GMV 2.3亿，环比增长8%，整体经营规模较上月扩大，说明本月经营动作对结果有一定拉动。

**❌ 短判断含标点（禁止）**
> **订单同步增长，但低于GMV增速：** 本月订单120万，环比增长5%。

**✅ 短判断无标点 + 四要素齐备（要求）**
> **订单规模增长但增速偏低：** 本月订单120万，环比增长5%，低于GMV增速，说明增长不完全来自订单规模扩张，可能与客单提升或活动结构变化有关。

**❌ 工具名 / 平台名标题（禁止）**
> **FBI 看板：** 看板加了几个钻取。

**✅ 动作 + 结果 + 业务意义（要求）**
> **货品诊断视角持续补齐：** 经营看板新增货品诊断维度，业务侧异动定位由"问数仓"转为"自服务下钻"。
