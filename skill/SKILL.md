# 阿里风格拉条子写作技能

## 何时使用

当用户提交中文工作汇报类原文，并希望改写为管理者会前可快速扫读的结构化写作时使用。

常见触发表达：
- "改成拉条子" / "阿里风格" / "结论先行"
- "重写月报 / 周报 / 复盘 / 总结"
- "结构化一下这个汇报"
- "管理者风格" / "老板要看的"

适用原文类型：月报、周报、项目复盘、数据分析结论、SQL/建表进度、BI看板汇报、业务诊断、经营分析。

### 三种输出模式

技能内部存在三种不同的输出形态，按用户触发表达**自动选择**：

| 模式 | 触发表达 | 输出形态 |
|---|---|---|
| **基础拉条子（半页扫读版）** | 改成拉条子 / 结论先行 / 周报 / 复盘 / 业务诊断 / 数据分析结论 | 单条总论点 + 3–5 条一级 + 紧凑二级，全文 ≤ 800 字 |
| **月报提交模式 · 数据/项目侧** | 月报 / 本月工作总结 + 输入主体是数据 / SQL / 看板 / Agent / Skill / 模型 / 系统 / API / 工具链等技术性工作流 | `**本月工作总结**` + 摘要段 + 4–6 条一级（项目名：价值判断）+ 每条 2–3 条二级 + 可选 `[图片]`，全文 900–1300 字 |
| **月报提交模式 · 运营子模式** | 月报 / 本月工作总结 + 输入主体是商户拜访 / 商家沟通 / 活动推进 / 货品跟进 / 履约问题 / 客诉处理 / 门店走访 / 招商 / 报名 / 补贴 / 价格 / 库存 / 商品 / 陈列 / 转化 / 复盘 / 协同推进 等业务运营动作 | `**本月工作总结**` + 摘要段 + 4–6 条一级（业务动作型标题）+ 每条 2–3 条二级 + 业务措辞，全文 900–1300 字 |

**模式分发逻辑（mode dispatch）**：

1. **触发关键词 = 月报 / 工作总结 / 提交给老板** → 进入月报提交模式（不输出半页拉条子）
2. **判断输入主体性质**：
   - 输入主要谈代码 / SQL / 数据基建 / 看板 / API / 模型 / 工具链 / Agent / Skill / 站点等**技术性工作流** → **数据/项目侧子模式**（详见"月报提交模式"章）
   - 输入主要谈商户 / 商家 / 活动 / 客诉 / 门店 / 走访 / 招商 / 货品跟进 / 履约 / 陈列等**业务运营动作** → **运营子模式**（详见"运营月报子模式"章）
   - **混合输入**（既有技术工作又有运营动作）→ **同时保留两类一级论点**，技术类一级用项目名标题、运营类一级用业务动作型标题，**不得**强行把一类风格套到另一类
3. **模糊场景**（"重写月报"但语气像"会前快速过一下"）→ 按拉条子半页版输出
4. **本技能用于通用工作汇报**——不局限于数据/技术月报；运营、品类、业务跟进、商户拜访、活动推进等非技术工作同样适用

**绝对禁止**：在运营输入上强加技术化措辞（详见"运营月报子模式 > 技术化措辞禁忌"）。

## 输出形态铁律（最高优先级）

无论上下文如何，本技能的回复**只输出最终改写后的拉条子内容**，且**必须从加粗总论点开始**。所有思考、抽取、归类、拟标过程一律内部默执行，**不得在输出中显形**。

### 严禁出现的"过程性"片段

| 类别 | 严禁短语（举例） |
|---|---|
| 流程引导 | "现在我来按照拉条子规范……" / "下面我开始" / "首先我会" |
| 抽取宣告 | "先做抽取" / "原文事实抽取" / "事实抽取如下" |
| 归类宣告 | "归桶" / "归类如下" / "我先把它分成几个一级" |
| 改写引导 | "以下是改写结果" / "改写如下" / "下面给出改写" |
| 自我总结 | "以上即为改写" / "整体改写完毕" / "希望能帮到您" |
| 客套开场 | "好的" / "明白" / "收到" / "下面汇报" |

判定法：如果一段文字描述的是"我正在做什么"或"我接下来要做什么"，而不是"对业务的判断"，就是过程性内容，必须删除。

### 加粗结构铁律（不得弱化）

输出**必须**严格使用以下三层加粗结构，缺一不可：

1. **一条加粗总论点**（首行，前后留空行）
2. **若干条加粗一级论点**（每条独立一行，前后留空行）
3. **每个二级子论点冒号前的加粗短判断**（形如 `**短判断：** 正文`）

仅扫读所有加粗位即应能看懂全文核心结论。如果加粗位被去掉后仍能读出完整意思，说明加粗结构没有承载判断，必须返工。

### 输出从首字符即为加粗总论点

- 不写"好的""明白""收到""下面是改写"等开场
- 不写"如上"——更不写"以上即为本次改写结果"等收口

## 输出层级（强制三层）

1. **总论点（1 条）** — 加粗。一句话点明本次汇报核心结论。
2. **一级论点（3–5 条；月报多工作流场景上限至 6 条）** — 加粗。每条是一句结论式判断（不是字段名）。
3. **二级子论点（每个一级下 2–4 条）** — 每条按下方强制格式书写。

## 二级子论点强制格式

```
**[短判断无标点]：** 事实 + 数据 + 解释 + 判断。
```

### 冒号前（短判断）硬约束

| 项 | 要求 |
|---|---|
| 长度 | 通常 8–18 个汉字 |
| 形态 | 结论式短句，不是字段名 |
| 禁用标点 | `,` `.` `;` `，` `。` `；` `、` 一律不得出现 |
| 禁用空标签 | `GMV：` `订单：` `客单价：` `数据集：` `看板：` `SQL：` 等单纯字段名一律不得作为短判断 |
| 禁用工具/平台名独立成标 | 仅写 `ODPS 工具链：` / `自助分析平台：` / `经营看板：` 这类工具名或平台名，不得作为短判断 |

判定法：去掉冒号后能不能读出"判断"？读不出就是字段名，必返工。

### 二级标题语义形态（落到月报场景的强约束）

二级标题必须是 **"动作 + 结果 / 状态 + 业务意义"** 的结构，让一个不熟悉工具名的事业部老板也能一眼看懂"做了什么 + 当前是什么状态 + 对业务有何意义"。

| ❌ 工具名 / 平台名标题 | ✅ "动作 + 结果 + 业务意义"标题 |
|---|---|
| `ODPS 工具链：` | `双端安装链路完成打通：` |
| `Qoderwork 数据连接：` | `数据连接底座初步建成：` |
| `FBI 看板：` | `货品诊断视角持续补齐：` |
| `自助分析平台：` | `业务侧自助拖拽跑通主路径：` |
| `AI 报告：` | `大模型月报生成跑通基础链路：` |

### 冒号后（正文）四要素

按顺序铺陈，可融合在 1–3 个完整中文句子内：

- **事实**：发生了什么动作 / 结果 / 现象
- **数据**：具体数字、占比、环比、同比、绝对值或区间
- **解释**：数据背后的原因 / 机制 / 结构性变化
- **判断**：对经营的意义、风险、或下一步含义

整段建议不超过 80 字。

## 业务价值语言（必做转换）

将"执行语言"改写为"业务价值语言"：

| 执行语言（不要） | 业务价值语言（要） |
|---|---|
| 建了一张订单宽表 | 订单宽表上线支撑多维经营分析 |
| 跑了一次 SQL | 完成订单回流校验数据一致性达标 |
| 上线了一个看板 | 经营看板上线管理层可日级追踪核心指标 |
| 优化了表结构 | 表结构治理后 BI 查询性能提升使用门槛降低 |
| 接了 N 个需求 | 完成 N 项业务分析需求支撑业务决策 |

## 管理者阅读偏好（强约束）

阿里风格拉条子的核心约束之一是：**管理者只读加粗文字也能抓到核心结论**。请按以下要求收口：

- **加粗结构自洽**：仅扫读总论点 + 一级论点 + 二级标题（冒号前），即可完整把握本次汇报的核心逻辑链。
- **加粗即结论非分类**：加粗位必须是结论式短判断，承载"是好是坏 / 是涨是跌 / 是稳是险"，不得是分类标签或字段名。
- **避免空泛归类标题**：禁止仅写 `经营情况`、`数据建设`、`问题风险`、`本月情况`、`后续工作` 等无判断的归类标题；如需沿用此类范式，必须叠加明确判断（如 `经营结果环比改善但增长结构偏单点` 而非 `经营情况`）。
- **加粗位不解释只判断**：事实、数据、机制解释一律放在冒号后正文，加粗位不堆细节，单条扫读即能给出判断。

## 工作流完整性（多工作流场景必读）

针对月报、季度复盘、年中汇报这类"多工作流并行"输入：

### 强约束

- 当原文清晰呈现 **4–6 条相互独立的工作流**时，**优先保留为 4–6 条独立的一级论点**，而非强行压缩到 3 条
- 月报场景中"完整性"优先于"美感型压缩"：宁可一级数量略多（最多 6 条），也不要把不同项目硬塞进同一条
- 当且仅当两条工作流在事实层面高度耦合（同一项目的不同阶段 / 同一目标下的两个抓手），才合并

### 一级论点数量调整

- 一般场景：3–5 条
- 月报多工作流场景：3–6 条（上限放宽至 6 条）
- 6 条以上：必须做合并取舍

### 顺序保留

- 用户原文中工作流之间已经有合理顺序时（按项目独立性 / 业务重要性 / 时间线），**保留原顺序**
- 不要为了套用"经营结果 / 经营动作 / 隐忧 / 后续动作"范式强行重排

### 不得静默丢弃

- 任何在原文中独立成段的工作流，都不得在输出中被省略
- 如某条工作流信息密度低（只有动作没有结果），仍以一级论点形式保留，并诚实写出"初步推进"或用业务价值语言描述其意义
- **不要把"5 条独立工作流的月报"输出成 3 条结构化总结**——月报本质是月度多工作流并行的状态扫描，结构化扫描不应损失工作流颗粒度

## 月报忠实扩写（Faithful expansion for monthly reports）

月报与阶段汇总场景下，**信息保留与可提交性**优先于"美感型压缩"。压缩到每条一级只剩一行二级判断、整篇全是工具名速记的输出，不算月报，只能算个人备忘录。

### 定义

允许在保留每条工作流原始事实的前提下，从单一**做了什么**扩写为四件事：

- **做了什么**（事实 / 动作 / 当前状态）
- **解决了什么问题**（这个动作消除/缓解了哪个原本的痛点）
- **创造了什么业务或团队价值**（对业务、用户或团队协同节奏的意义）
- **支撑了什么后续能力**（为下一步迭代、复用、沉淀提供了什么基础）

这是 **"忠实扩写"（faithful expansion）**——所有扩写内容必须能从用户原文事实里**自然推得**，不是模型自己"补充"出来的。

### 严禁虚构（hard rule）

模型在做月报扩写时，**绝对不得**凭空引入用户原文中没有的：

- 新数字 / 新指标 / 新百分比
- 新业务结果（如 GMV 提升、订单提升、转化率提升等）
- 新项目 / 新工作流
- 新用户反馈 / 新满意度评价
- 新采纳率 / 新落地状态
- 任何输入未暗示的新系统能力 / 新功能 / 新接入方

判定法：写完每条二级后问三个问题——

1. 这件事用户原文写过吗？（事实 / 动作 / 状态）
2. 这条二级所承载的"问题 / 价值 / 后续"，是从原文事实**自然推得**的吗？还是我"自己补"上去的？
3. 如果让用户对着原文逐句核对，他能否说"是的，意思就是这个"？

任一答"否"，删掉或改写——宁可一句二级缺一个维度，也不能虚构。

### 月报场景具体要求

1. 月报或阶段汇总场景下，**禁止过度压缩**——不得为了简洁而把一条工作流压成单条二级。
2. 输入若包含 **4–6 条清晰工作流**，输出**保留为 4–6 条独立一级论点**。
3. 每条一级论点**通常包含 2–3 条二级短判断**，覆盖事实、问题/价值、后续动作。
4. **避免一级仅 1 条二级**——仅在原文该工作流信息确实极少（一两句话）时作为例外。
5. 每条二级正文应当尽量同时铺陈三件事：
   - 动作 / 事实
   - 解决的问题（或对应的痛点）
   - 业务价值或后续意义
6. **措辞保持克制**——扩写是"把价值说清楚"，不是"把语气放大"。
7. **严禁引入用户原文未出现的放大型词**（即使为了让标题更有"力度"也不行）：
   - 明显提升
   - 大幅提升
   - 完全打通
   - 零门槛
   - 全自动
   - 闭环完成
8. **优先使用克制型替换**：
   - 降低使用门槛
   - 减少重复支持成本
   - 初步打通
   - 基本跑通
   - 形成能力雏形
   - 为后续迭代提供基础
   - 支撑后续沉淀

### 扩写边界示例

| 用户原文 | ✅ 忠实扩写 | ❌ 自由扩写（虚构） |
|---|---|---|
| "mac 和 windows 双端都搞定了，安装比之前简单多了" | "双端安装链路完成打通，相较此前安装较为简化，团队同事已开始使用，使用门槛降低" | "双端安装零门槛，使用率大幅提升至 80%" |
| "Agent 工作台接了几个数据源，能跑基础查询" | "Agent 工作台已接入若干数据源，可支撑基础查询场景跑通，形成数据连接初步底座" | "Agent 工作台接入 12 个数据源，覆盖率 95%，全自动化分析" |
| "AI 报告链路在探索，准确性还要看" | "大模型月报生成链路初步跑通，已可生成月报草稿，准确性仍需进一步观察" | "AI 报告闭环完成，月报生成完全替代人工，效率显著提升" |

判定法：左列是用户写过的，右列是模型自己加的——任何"看起来更漂亮"但用户没说过的内容都属于右列，必须删除。

## 月报提交模式（Monthly report submission mode）

这一节定义"提交给老板的正式月报"输出形态。它是**忠实扩写章节的上层包装**——继承所有"4–6 条一级 / 每条 2–3 条二级 / 不得虚构"约束，并在此基础上附加四件事：**月报标题与摘要段、项目名+价值判断的一级标题、3 条二级的稳定节奏、`[图片]` 占位符保留**。

### 何时进入此模式

当用户的触发表达包含以下任一关键词，**默认按月报提交模式输出**：

- 月报 / 本月月报
- 本月工作总结 / 本月总结
- 工作总结
- 阶段总结
- 提交给老板 / 给老板看

判定法：用户语气是"提交一份汇报材料"还是"会前扫一眼的速记"。前者走月报提交模式，后者走基础拉条子。

### 输出结构骨架（强制）

月报提交模式的输出**必须**严格遵循以下结构（顺序与层级不得颠倒）：

```
**本月工作总结**

[摘要段落 — 100–180 中文字]

**[项目/模块名 1]：[价值判断]**

- **[短判断 1]：** [事实 + 解决问题 + 业务价值或后续意义]
- **[短判断 2]：** [事实 + 解决问题 + 业务价值或后续意义]
- **[短判断 3]：** [下月动作或后续支撑]

[图片]   ← 仅当原文该模块后有 [图片] 时保留

**[项目/模块名 2]：[价值判断]**

[继续 4–6 条一级，每条同样结构]
```

### 摘要段落（紧跟"本月工作总结"）

摘要段落应当承载三件事：

- **主要工作方向**：本月推进的几条工作流（按原文出现顺序列举即可）
- **整体价值判断**：这些工作整体对业务/团队的意义（不放大、不虚构）
- **"一方面…另一方面…"结构**：当本月工作明显分两侧（如"工具与连接侧 / 分析能力侧"、"建设侧 / 治理侧"），建议使用此结构归类

长度 **100–180 中文字**——能让事业部老板在 30 秒内把握本月主线。摘要段不写"我们觉得 / 整体来看 / 综上所述"等口语过渡。

### 一级标题格式（强制 `项目/模块名：价值判断`）

| ❌ 过度压缩（拉条子半页版形态） | ✅ 月报提交模式 |
|---|---|
| `**双端使用门槛降低**` | `**跨平台命令行工具：双端安装链路打通降低本地使用门槛**` |
| `**数据连接初步建成**` | `**Agent 工作台数据打通：连接数据底座支撑业务自助查询**` |
| `**自助分析跑通**` | `**自助分析站点：沉淀自助查数能力减少重复取数成本**` |
| `**经营看板补齐**` | `**基础经营看板：维度持续补齐支撑会上扫读**` |
| `**AI 报告探索**` | `**AI 报告链路：草稿生成跑通基础链路待小批量验证**` |

要求：

- 一级标题保留**用户原文中的项目/模块/工具名**（脱敏后），让老板能在标题里看到"这是哪个项目的进展"
- 一级标题在 `：` 后承载**价值判断**——做了什么 + 这件事对业务/团队的意义
- 长度 18–32 字（比拉条子半页版的 10–22 字更长，因为承载了项目名）
- 一级标题不得仅写工具名（违反第 4 节工具名独立成标禁令）
- 不得为了"短"而把项目名删掉（拉条子半页版可压缩，月报提交版必须保留项目名）

### 二级子论点（每条一级通常 2–3 条）

二级子论点格式与基础拉条子一致：

```
**[短判断]：** 事实 / 动作 + 解决的问题 + 业务价值或后续意义
```

月报提交模式的额外要求：

- **每条一级下通常 2–3 条二级**（一般为：本月动作 / 关键状态或问题 / 下月动作）
- **二级正文必须可被反向回查**：每个事实必须能在用户原文里找到对应的句子或暗示
- 短判断长度在月报提交模式下**放宽到 4–18 字**——允许更短的"动作 / 结果"型人写月报标题，只要不是空字段名

#### 短判断长度（月报提交模式放宽）

| 长度 | 月报提交模式 | 半页拉条子 |
|---|---|---|
| 4–7 字（短人写月报形态）| **允许**——只要包含动作 / 结果词 | 不推荐 |
| 8–18 字（标准）| 推荐 | 推荐 |
| 19–22 字（边界）| 可放行 | 可放行 |

#### 短判断形态（月报提交模式更接近人写笔记）

月报提交模式优先**短而具体的动作 / 结果型**短判断，避免**过度抽象的 AI 化短判断**。

| ✅ 短而具体（人写月报形态） | ❌ 过度抽象（AI 化形态） |
|---|---|
| 安装链路打通 | 双端使用门槛下行支撑团队铺开 |
| 一键使用落地 | 主路径形成能力雏形 |
| 安装体验优化 | 跨端使用条件得到补齐 |
| 数据桥梁建设 | 数据连接底座初步形成 |
| 查询能力迭代 | 多端能力获得阶段性进展 |
| 基础功能补齐 | 多项能力初步成型 |
| 后续能力承接 | 后续能力沉淀闭环 |
| 需求承接 | 业务取数主路径跑通 |
| 查询能力沉淀 | 数据查询底座初步成型 |
| 使用路径前置 | 使用门槛阶段性下行 |
| 需求协同推进 | 协同链路推进取得进展 |
| 曝光效率拆分 | 曝光效率主路径分析 |
| 连带分析补充 | 多维分析能力雏形补齐 |
| 报告主题设计 | 主题分析能力初步成型 |
| 链路初步跑通 | 端到端链路阶段性闭环 |
| 阶段结果可用 | 阶段成果初步可用支撑 |

判定法：把短判断单独读出来，听起来像不像一个老板会在月会上自然说出的话。听起来像"模型自己拼出来的高大上短语"就替换。

**禁止**（仍然必须避免）：

- 字段名：`GMV：` / `订单：` / `数据：` / `看板：` / `SQL：` / `情况：` / `现状：`
- 工具名独立成标：`ODPS 工具链：` / `FBI 看板：`
- 含禁用标点的短判断（标点列表见第二节 2.2）

### `[图片]` 占位符保留（强约束）

若用户原文中某个模块后有 `[图片]`（或 `[image]`、`[截图]`、`[demo 截图]` 等占位符），**必须**在改写后该模块的最末尾对应保留 `[图片]`。

- ✅ 保留位置：紧跟在该一级模块的所有二级 bullet 之后，独立成行
- ✅ 保留写法：原样照抄（`[图片]` → `[图片]`）
- ❌ 不要因为"看起来不规范"就删除 `[图片]` 占位符
- ❌ 不要在用户没写 `[图片]` 的模块凭空补一个
- ❌ 不要把 `[图片]` 改写为 `（此处见截图）` 等"自作主张"的表述

### 自然语言度（与"AI 模板话术"的边界）

月报提交模式**必须**保持自然商务语言。**严禁出现以下"不自然 AI 短语"**（即便它们看起来"专业"）：

| ❌ 不自然 AI 短语 | ✅ 自然商务替换 |
|---|---|
| 使用门槛下行 | 降低使用门槛 / 使用门槛降低 |
| 能力获得 | 形成能力 / 沉淀能力 / 具备 X 能力 |
| 数据不可达瓶颈 | 数据无法对齐 / 业务无法直接取数（保留具体场景）|
| 多项能力初步成型 | 多个方向均形成阶段性进展 / 各方向按节奏推进 |
| 用户不再受操作系统差异困扰 | 跨端使用条件得到补齐 |
| 消除瓶颈 | 缓解 / 减少阻力 / 降低协同成本 |
| 多端能力获得 | 双端可用 / 双端可装 |
| 流程闭环已达成 | 链路初步跑通 / 基本跑通 |

判定法：把这条短语单独读出来——听起来像不像一个老板在月会上会自然说出的话。听起来像 AI 模板话术就替换。

### 不得引入的扩写（与忠实扩写规则一致）

月报提交模式即便结构更长更"正式"，扩写边界**与"月报忠实扩写"章节完全一致**：

- 不得引入新数字 / 新指标 / 新百分比
- 不得引入新业务结果 / 新落地状态
- 不得引入新用户反馈 / 新满意度
- 不得引入新接入方 / 新系统能力
- 中性语言不得改写为正向语言（如"反馈整体可用"不得改为"反馈正向"）

### 不得引入的放大型词汇

与"业务措辞克制"一致：

- 零门槛 / 大幅提升 / 明显提升 / 完全打通 / 全自动 / 闭环完成 / **消除瓶颈**

> 注：`消除瓶颈` 是常见 AI 模板话术——月报提交模式严禁。请用 `缓解 X 阻力` / `减少 X 协同成本` / `降低 X 门槛` 等克制表达。

### 命名工作项保留（named work item preservation）

如果用户原文中给出了具体的项目名 / 系统名 / 工具名 / Skill 名 / 站点名 / 看板名 / 模型名 / 报告名，**输出必须原样保留**，不得替换为通用类别词。

| ❌ 把命名项目泛化（损失项目颗粒度） | ✅ 保留命名项目（人写月报形态）|
|---|---|
| `ODPSCMD Skill` → `ODPS 命令行工具` / `跨平台命令行工具` | 保留 `ODPSCMD Skill` |
| `基础 FBI 看板` → `基础经营看板` / `经营 BI 看板` | 保留 `基础 FBI 看板` |
| `DeepinSight 站点` → `自助分析站点` / `数据自助站点` | 保留 `DeepinSight 站点` |
| `Agent 工作台` → `Agent 平台` / `AI 助手` | 保留 `Agent 工作台` |
| `AI 报告输出` → `AI 报告链路` / `大模型月报` | 保留 `AI 报告输出` |

要求：

- **保留原始大小写**——`ODPSCMD` 不得改为 `Odpscmd` 或 `odpscmd`
- **保留品牌前缀**——`基础 FBI 看板` 不得只剩 `基础看板` 或 `FBI 看板` 或 `经营看板`
- **保留 Skill / 站点 / 工作台 / 看板等容器后缀**——若用户写"`ODPSCMD Skill`"就不得只剩"`ODPSCMD`"
- **仅当用户显式要求脱敏**（如"匿名化 / 隐去内部名称 / 不要写品牌"）时才允许替换为通用类别词

判定法：把摘要段 + 一级标题给一个不熟悉项目的同事看，他能否一眼看出"这是哪些具体项目的进展"。看不出说明命名信息丢失。

### 禁止过度推断（no unsupported inference）

模型**不得**在用户原文之外引入以下"看似合理"的推断——这些推断即便读起来像月报，也会让月报失真：

| 推断维度 | ❌ 不得引入 |
|---|---|
| UI / 操作行为 | `自行拖拽查询` / `一键导出` / `点击即用` |
| 采纳 / 依赖状态 | `不再依赖人工中转` / `已全员采纳` / `数据团队不再承接此类需求` |
| 自动化程度 | `完整自动化闭环` / `全流程自动化` / `自动化覆盖所有场景` |
| 未来扩展方向 | `后续可扩展至更多数据域` / `后续可扩展至货品 / 流量等维度` / `下季度可推广至全公司` |
| 业务效果 | `业务效率提升 / 决策速度加快` / `提升老板满意度` |
| 用户感受 | `用户不再受系统差异困扰` / `用户体验明显改善` |
| 系统能力 | `Windows 用户可在本地直接执行 ODPS 查询` / `Agent 可承接所有取数场景` |

**克制可追溯替换**：

| ❌ 推断式表达 | ✅ 克制可追溯替换 |
|---|---|
| 业务取数不再依赖人工中转 | 减少重复取数和临时响应成本 |
| 自行拖拽查询 | 业务可自助拖字段查看简单数据（贴回原文） |
| 消除数据瓶颈 | 缓解 X 数据无法对齐的具体场景 |
| 后续可扩展至更多数据域 | 下月将订单与会员两个数据域接入（贴回原文）|
| 完整自动化闭环 | 链路初步跑通 / 基本跑通 |
| 用户不再受系统差异困扰 | 双端可用 / 双端可装 / 跨端使用条件得到补齐 |

判定法（每条二级写完后问）：

1. 这条二级里的每件事，是否都能在用户原文里**找到原始句子或暗示**？
2. 如果让用户对着原文逐句核对，他会不会皱眉说"我没说过这个"？

任一答"是"（即用户会皱眉），删掉或改写为更贴近原文的表述。

### 不得为凑足条数而虚构后续（do not force future plans）

每条一级**通常 2–3 条二级**——但**绝不**为了凑足 3 条而虚构 `后续待...` / `下月待...` / `下季度计划` 等用户原文未提及的未来动作。

判定流程：

1. 用户原文显式提到该工作流的"下月动作 / 后续方向"了吗？
   - 是 → 写成第 3 条二级（标准三件事节奏）
   - 否 → 进入步骤 2
2. 用户原文是否给出该工作流"当前状态"足够支撑 3 条独立的现状型二级？
   - 是 → 写成 3 条二级，使用**当前状态价值型**短判断（见下文）
   - 否 → 接受 **2 条二级**——不得虚构第 3 条

**当前状态价值型短判断（不依赖未来动作）**：

| 类别 | 短判断举例 |
|---|---|
| 能力沉淀 | `查询能力沉淀` / `数据桥梁建设` / `安装能力沉淀` |
| 路径与体验 | `使用路径前置` / `安装体验优化` / `查询路径打通` |
| 功能补齐 | `基础功能补齐` / `维度持续补齐` / `数据桥梁建设` |
| 需求 / 承接 | `需求承接` / `后续能力承接` / `需求协同推进` |
| 链路 / 阶段 | `链路初步跑通` / `阶段结果可用` |

| ❌ 虚构后续 | ✅ 当前状态价值表述 |
|---|---|
| `后续待小批量验证后扩展到全部数据域`（用户没说"全部数据域"）| `阶段结果可用，待下月验证扩展边界` |
| `后续待 Q2 推广至公司其他事业部`（用户没说推广）| `当前能力具备组内自助使用条件` |
| `后续待补齐 X / Y / Z 维度并打通自动化报告`（用户没说 X/Y/Z）| `维度持续补齐` |

## 运营月报子模式（Non-technical operations monthly report mode）

这是月报提交模式的**第二个子模式**，与"数据/项目侧子模式"并列。当用户的输入主体是**业务运营动作**（商户、活动、客诉、门店、招商、货品跟进等），技能必须按运营月报形态写——而不是把运营工作硬套上数据基建的技术化措辞。

> 本技能不止服务数据分析师。运营、品类、业务、招商、客服、商户经理等非技术岗位也是核心用户。**他们写月报不会、也不该用技术化的"链路 / 底座 / 模型"词汇。**

### 触发输入主体（如何识别运营子模式）

当输入主要包含以下任一类业务运营动作时，进入运营子模式：

| 类别 | 触发关键词 |
|---|---|
| 商户 / 商家 | `商户拜访` / `商家沟通` / `商户问题` / `商户反馈` |
| 活动 / 报名 | `活动推进` / `活动报名` / `活动复盘` / `补贴` |
| 货品 / 价格 | `货品跟进` / `价格` / `库存` / `商品配置` / `陈列` |
| 履约 / 客诉 | `履约问题` / `客诉处理` / `投诉` / `售后` |
| 门店 / 走访 | `门店走访` / `门店诊断` / `走访` / `拜访` |
| 招商 / 招募 | `招商` / `商户招募` / `引入新商户` |
| 协同 / 复盘 | `协同推进` / `跨团队对接` / `月度复盘` / `策略调整` |
| 转化 / 经营 | `转化` / `日常执行` / `经营改善` |

判定法：把输入读一遍，问"这个人是写代码 / 看数据 / 调系统 / 训模型 / 接 API 的吗？"
- 是 → 数据/项目侧子模式
- 否（他在拜访商户、推活动、处理客诉、走访门店、做招商、跟价格库存、协同跨团队等）→ **运营子模式**

### 输出结构骨架（与数据/项目侧子模式一致 + 业务化语言）

```
**本月工作总结**

[摘要段落 100–180 中文字]

**[业务动作 1]：[价值判断]**

- **[短判断 1]：** [事实 + 解决问题 + 业务价值或后续动作]
- **[短判断 2]：** ...
- **[短判断 3]：** ...

[继续 4–6 条一级，每条同样结构]
```

### 一级标题格式（业务动作型，不是项目名型）

运营子模式的一级标题用 **`业务动作：价值判断`** 形态——核心是"做了什么类型的业务工作 + 这件事推进了什么"，不要套数据/项目侧子模式的"项目名：价值判断"形态（除非输入里就有具体项目名）。

| ✅ 业务动作型（运营子模式） | ❌ 技术化套用 |
|---|---|
| `重点商户跟进：围绕核心商户问题推进经营改善` | `商户问题链路完成打通降低沟通门槛` |
| `活动报名推进：完成商户沟通提升活动参与基础` | `活动能力底座初步建成支撑后续活动` |
| `货品问题排查：聚焦价格库存和曝光问题补齐运营动作` | `货品诊断系统能力初步形成` |
| `客诉问题处理：推动高频问题闭环降低后续风险` | `客诉处理形成闭环能力支撑后续治理` |
| `商户走访复盘：沉淀一线反馈支撑后续策略调整` | `走访链路完成打通形成数据采集底座` |

要求：

- 一级标题动作部分覆盖**实际业务工作类型**（拜访 / 推进 / 排查 / 处理 / 复盘 / 沉淀 / 跟进 / 招募 / 协同），不强行项目化
- 价值判断部分用**业务措辞**（推进经营改善 / 提升参与基础 / 沉淀一线反馈 / 降低后续风险 / 支撑后续策略调整）
- 长度 18–32 字
- **若输入里给了具体项目名 / 商户名 / 活动名**（如"双 11 大促"、"XX 商户"），照样保留——参见"命名工作项保留"

### 二级短判断（业务动作 + 结果型）

二级短判断同样允许 **4–18 字**的短人写月报形态。运营月报常见形态：

| ✅ 业务动作 + 结果型短判断 | ❌ 技术化形态 |
|---|---|
| 商户问题完成梳理 | 商户问题链路打通 |
| 活动报名持续推进 | 活动能力底座建成 |
| 价格库存问题集中跟进 | 价格库存数据底座补齐 |
| 一线反馈完成沉淀 | 一线反馈链路初步形成 |
| 跨团队协同持续推进 | 跨团队协同底座搭建 |
| 后续风险提前识别 | 后续风险监控能力打通 |
| 商户走访完成 | 商户走访能力沉淀 |
| 客诉处理路径明确 | 客诉处理闭环达成 |
| 重点商户报名完成跟进 | 重点商户报名链路打通 |
| 协同节奏完成沉淀 | 协同自动化闭环 |

### 技术化措辞禁忌（强约束）

运营子模式下，**严禁出现以下技术化套词**——除非用户原文显式使用：

| ❌ 技术化措辞 | ✅ 运营自然替换 |
|---|---|
| 数据底座 | 商户反馈记录 / 一线信息沉淀 |
| 链路打通 | 完成对接 / 完成梳理 / 持续推进 |
| 系统能力 | 协同节奏 / 处理路径 / 业务动作 |
| 技术基建 | 协同机制 / 工作流程 / 协同口径 |
| 模型能力 | （运营子模式一般不应出现"模型"——如出现请删除）|
| 自动化闭环 | 持续推进 / 阶段性完成 / 协同推进到位 |
| 数据连接 | 信息对齐 / 跨团队对接 |
| 数据采集 | 一线反馈收集 / 走访沉淀 |
| 接口对接 | 跨团队对齐 / 沟通对齐 |

**判定法**：把这条短语读给一个不写代码、不看数据的运营同事听——他会皱眉说"这是技术那边的话，我们不这么写"吗？会皱眉就替换。

### 推荐的运营措辞（克制 + 业务）

| 类别 | 推荐用词 |
|---|---|
| 推进类 | `推进` / `跟进` / `继续推进` / `持续推进` |
| 对齐类 | `对齐` / `梳理` / `沉淀` / `同步` |
| 协同类 | `协同推进` / `跨团队对接` / `协同分工明确` |
| 收口类 | `复盘` / `沉淀` / `形成清单` / `形成口径` |
| 价值类 | `降低沟通成本` / `减少重复协同` / `为后续策略调整提供依据` / `支撑后续推进` |

### 不得虚构（与数据/项目侧子模式一致 + 运营特殊禁忌）

运营场景特别容易"被推断"的虚构内容：

| 类别 | ❌ 不得引入（除非用户原文明确给出）|
|---|---|
| GMV / 订单 / 转化数字 | `本月活动带动 GMV 提升 X%` / `订单环比 +X%` |
| 商户反馈 | `商户满意度提升` / `商户对活动反响热烈` / `商户给予正面评价` |
| 活动结果 | `活动效果超预期` / `本次活动 ROI 创新高` / `转化率明显改善` |
| 商户采纳 | `商户已全员报名` / `商户主动配合` / `商户对策略高度认可` |
| 业务影响 | `推动品类整体增长` / `带动业务效率明显提升` |

**特别约束**：当用户只给"执行记录"（"我拜访了 X 家"、"我对接了 Y 次"、"我做了 Z 复盘"）时，把这些转写为**结构化工作进展**，**不要**自己造业务影响。

### 仅在用户给出时才使用的运营具体词

- 具体商户名 / 商家名（出现就保留）
- 活动名（出现就保留——参见"命名工作项保留"）
- 具体数字（出现就保留；不出现就用定性表述）
- 具体反馈（出现就引用原文表述；不出现就写"已识别 / 已沉淀 / 已对齐"）

详见 `references/examples.md`：
- 示例 10：商户拜访月报金示例（运营子模式 + 5 条工作流 + 业务动作型标题）
- 示例 11：活动运营月报金示例（运营子模式 + 4 条工作流 + 不虚构活动结果）

## 业务措辞克制（强约束）

绝不超出用户事实做"放大型表达"。即便用户语气模糊或乐观，也必须以克制、商务的拉条子风格收口。

### 禁用放大型词汇（除非用户原文明确使用）

| 禁用 | 原因 |
|---|---|
| 零门槛 | 绝对化，几乎不可能成立 |
| 大幅（含"大幅提升"） | 副词放大，需要数据支撑 |
| 明显提升 | 暗示具体涨幅，但通常无数据支撑——属于"看似克制实则放大" |
| 完全打通 | 绝对化，多数场景仍属"初步" |
| 全自动 | 绝对化，常常是半自动 |
| 闭环完成 | 绝对化，多数仍是"链路初步跑通" |
| 显著 / 极大 / 巨大 | 副词放大，无数据支撑时滥用 |

### 推荐替换（克制型业务措辞）

| 放大型 | 克制型 |
|---|---|
| 零门槛 | 降低使用门槛 / 减少重复支持成本 |
| 大幅提升 / 明显提升 | 提升至 ... 水位（有数据时）/ 改善 / 较此前简化 |
| 完全打通 | 初步打通 / 链路打通 |
| 全自动 | 自动化（保留半自动事实）|
| 闭环完成 | 基本跑通 / 形成雏形 / 链路初步闭环 |
| 产品化落地 | 形成 Demo 雏形 / 初步可试用 |
| 支撑全流程 | 为后续迭代提供基础 / 支撑后续沉淀 |

### 措辞偏好原则

- 当用户写"成功""跑通""上线"时：用"完成上线" / "链路打通"，**不升级为"全面贯通"**
- 当用户写"做了一版 demo / 雏形"时：用"形成雏形" / "Demo 跑通"，**不升级为"产品化落地"**
- 当用户写"还在观察 / 还需迭代"时：用"持续观察 / 待迭代"，**不掩盖为"达成阶段目标"**
- 即使为了让标题"够有力"，也不得把方向性判断写成绝对化判断

## 缺数据时的处理（不得虚构 + 不得滥用占位符）

### 禁止虚构

- 绝对禁止编造数字、占比、环比、同比

### 占位符使用边界

`待补充：XX数据` 仅在以下情况使用：

1. 该指标是该段二级论点的核心结论（缺它，论点站不住）
2. 用户原文清晰暗示此处应有数据（如"涨了一些"指方向但未给数）
3. 该数据是经营决策的关键依据（管理层会前必看）

**正常月报改写中，全文 `待补充：` 不超过 2 处**。仅当用户**显式要求**做"数据完整性盘点"或"数据齐备性检查"时不受 2 处限制。

### 不应使用占位符的情况

- 数据可有可无、用方向词或定性判断替代不损失结论的情况
- 仅为"显得严谨"而堆叠的字段（如"覆盖三域字段共 待补充：字段总数"——字段总数本就不影响结论）
- 已经写了定性判断的句子，不要再叠加占位符

### 替代方案：定性判断

如果原文既无数据也无方向词，**优先写定性判断而非占位符**。

- ❌（占位符滥用）：`覆盖支付、退款、物流三域字段共 待补充：字段总数`
- ✅（定性判断）：`覆盖支付、退款、物流三域字段，BI 多维交叉查询无需多表 join`

## 语气

- 克制、商务、扫读友好
- 不出现："我们觉得 / 大概 / 应该 / 差不多 / 估计 / 感觉"
- 不滥用："非常 / 极大 / 巨大 / 显著 / 大幅"（除非有具体数据支撑）
- 不出现感叹号 `！` `!`
- 不输出客套开场白与结尾感谢

## 工作流（内部默执行 / 不得在输出中出现）

以下 6 步是模型在内部需要完成的处理。**任何一步都不得在输出中显形**：不得宣告"我现在开始抽取"，不得列出"原文事实抽取如下"，不得说"以下是改写结果"。模型直接以加粗总论点作为输出的第一行。

1. **抽取（默）**：从原文捞出所有事实、动作、数字、原因、风险、下一步
2. **归类（默）**：归入 3–5 条（月报多工作流可至 6 条）一级论点。常用归类范式：
   - 经营结果 / 经营动作 / 经营隐忧 / 后续动作
   - 进展 / 数据 / 风险 / 下一步
   - 业务问题 / 数据现象 / 根因判断 / 行动建议
   - **多工作流场景**：按工作流独立成一级（每条工作流一个一级，附带各自的下月动作）
3. **拟标（默）**：为每条二级子论点拟一个 8–18 字短判断（无禁用标点、非字段名、动作 + 结果 + 业务意义）
4. **填段（默）**：用 1–3 句话补齐"事实 + 数据 + 解释 + 判断"
5. **回写总论点（默）**：基于一级论点回写一句加粗总论点
6. **自检（默）**：执行 `references/checklist.md` 12 项检查后再输出

输出形态：以加粗总论点起笔，以最后一条二级子论点收尾。

## 输出长度

- 最终全文（不含原文回放）一般不超过 800 字
- 一级论点 3–5 条；月报多工作流场景上限至 6 条
- 每个一级下二级 ≤ 4 条
- 单条二级正文 ≤ 80 字
- `待补充：` 占位符正常场景下不超过 2 处

## 完整输出形态示例（精简）

> **本月经营整体稳中有进结构性隐忧需提前修复**
>
> **经营结果环比改善但增长结构偏单点**
>
> - **GMV 保持增长环比提升：** 本月 GMV 2.3 亿，环比 +8%，盘子较上月扩大约 1700 万，说明经营动作对结果端有正向拉动。
> - **订单规模增长但增速偏低：** 本月订单 120 万，环比 +5%，低于 GMV 增速 3 个百分点，增长更多来自客单提升而非订单扩张。
>
> **经营隐忧需提前暴露**
>
> - **新客次月留存承压：** 次月留存 待补充：次月留存数据，仍处下行通道，反映拉新质量与承接动作之间存在断点，应优先排查首单后 7 日触达。
>
> **后续动作聚焦两件事**
>
> - **优先修复新客次月留存：** 立项次月留存专项，由用户增长团队负责，月底前完成首单后 7 日触达 + 14 日召回 SOP 落地。
> - **私域触达节奏对齐目标：** 私域运营节奏由月触达 2 次提升至 4 次，目标本月完成沉淀进度追平计划。

## 关键对照（再次强调）

**❌ 字段名式标签（禁止）**
> **GMV：** 本月GMV 2.3亿，环比增长8%。

**✅ 结论式短判断（要求）**
> **GMV保持增长环比提升：** 本月GMV 2.3亿，环比增长8%，整体经营规模较上月扩大，说明本月经营动作对结果有一定拉动。

**❌ 短判断含标点（禁止）**
> **订单同步增长，但低于GMV增速：** 本月订单120万，环比增长5%。

**✅ 短判断无标点 + 四要素齐备（要求）**
> **订单规模增长但增速偏低：** 本月订单120万，环比增长5%，低于GMV增速，说明增长不完全来自订单规模扩张，可能与客单提升或活动结构变化有关。

**❌ 工具名 / 平台名标题（禁止）**
> **FBI 看板：** 看板加了几个钻取。

**✅ 动作 + 结果 + 业务意义（要求）**
> **货品诊断视角持续补齐：** 经营看板新增货品诊断维度，业务侧异动定位由"问数仓"转为"自服务下钻"。
